## 3. 남은 문제

### R-001 [P2] 살아 있는 요청의 잠금을 시간만으로 넘겨주고, 이전 요청이 새 잠금까지 해제함

**위치:** `chatbot/conversation.py:104–112`, 연결 경로 `server/routes.py:118–122, 147–153`.

`acquire()`는 `busy_since`가 300초 이상 오래됐으면 기존 생성 작업이 실제 끝났는지 확인하지 않고 새 요청에 잠금을 준다. 이후 `release()`는 어느 요청이 얻은 잠금인지 확인하지 않고 `busy_since = None`으로 만든다. 저장 시에도 해당 요청이 아직 유효한 소유자인지 검사하지 않는다.

**재현 절차와 결과:** 모델 대역의 완료 여부는 이벤트로 제어하고, 저장소 시계만 진행시켰다. 기본 `busy_timeout_seconds=300` 값은 변경하지 않았다.

1. 요청 A가 같은 세션에서 생성 중이다. 이때 다른 요청은 정상적으로 409를 받는다.
2. 저장소 시계를 301초로 진행한다. A가 여전히 실행 중인데 요청 B도 생성을 시작한다.
3. A를 먼저 완료시킨다. B가 여전히 생성 중인데 A의 finally가 B의 잠금까지 해제해 `busy_since`가 None이 된다.
4. 요청 C까지 200으로 진행된다. B와 C도 겹친다.
5. A/B/C 모두 200으로 끝났고, 저장 순서는 A → C → B였다. B의 모델 입력에는 A의 턴이 없었다.

**영향:** 5분을 넘는 생성·스트림이나 지연 상황에서 원래 B-006의 대화 정합성 문제가 다시 생긴다. 오래된 요청의 완료가 최신 잠금 상태를 깨뜨려 추가 중첩도 허용한다. 120초 로컬 스트림 대기 제한은 다음 토큰까지의 제한이므로 총 생성 시간을 300초 이하로 보장하지 않는다. 실제 서비스에서 5분 지연이 발생했다고 주장하는 것이 아니라, 그러한 조건의 제어 흐름을 모의 시간으로 재현했다.

**기존 보고서의 알려진 한계와 차이:** 수정 보고서는 연결이 시작되기 전 끊긴 경우 최대 5분 동안 잠금이 남는 점을 적었다. 여기서는 기존 작업이 정상적으로 살아 있어도 5분 후 동시 실행이 허용되며, 이전 작업이 다른 요청의 잠금을 지우는 별도 정합성 문제를 확인했다.

**수정 방향:** 시간 만료만으로 살아 있는 생성의 소유권을 덮어쓰지 않도록 한다. 요청별 소유 토큰을 두어 저장·해제 시 소유권을 검증하고, 만료된 요청의 결과가 늦게 도착해도 새 요청 상태를 바꾸지 못하게 해야 한다. 만료 후 새 요청을 받는 정책이라면 기존 생성의 취소 또는 오래된 결과 무효화까지 일관되게 처리한다. 토큰 검사 없이 타임아웃 숫자만 늘리는 것은 근본 해결이 아니다.

**완료 확인 조건:** 모의 시간 301초에서도 살아 있는 요청의 보호가 유지되거나, 만료된 요청이 확실히 무효화돼 늦은 저장·release가 새 작업에 영향을 주지 않아야 한다. 다른 세션의 병렬 처리는 유지한다.

**베이스라인 영향:** API/로컬 양쪽이 사용하는 공통 세션 저장소의 문제이므로 최종 확정 전에 보완을 권장한다.

### R-002 [P2, 로컬 경로] 소비자 타임아웃·종료 후에도 모델 생성이 계속됨

**위치:** `chatbot/backends/local_backend.py:118–126`.

새 코드의 `queue.Empty` 처리는 소비자에게 504를 반환하지만 생성 스레드를 정리하지 않는다. 타임아웃 분기에서는 `worker.join()`에도 도달하지 않으며, 소비자가 `generator.close()`로 나가는 경우도 취소 처리가 없다. `daemon=True`는 프로세스 종료를 막지 않는 설정일 뿐 현재 모델 연산을 취소하지 않는다.

**재현:** 원본 `stream()`과 `_generation_error()`를 AST로 추출해 큐/모델 대역으로 실행했다. 긴 대기 없이 확인하기 위해 대역 실행의 대기 제한만 120초에서 0.03초로 줄였다.

- 즉시 OOM 오류: 사용자 메시지와 BackendError(502)가 전달됨. 원래의 무한 대기 증상은 해결됐다.
- 첫 토큰 이후 대기 제한 초과: 소비자는 504를 받았지만 생성 작업은 계속 실행 중이었다.
- 첫 토큰 이후 소비자 close: 생성 작업이 계속 실행 중이었다.
- 두 경우 모두 모델 대역을 다시 진행시키면 이미 소비자가 없는 큐에 토큰과 종료 신호가 추가됐다.

**영향:** 화면에서 실패로 끝나도 CPU/GPU 작업이 남을 수 있다. 새 시도와 겹치면 자원 낭비나 메모리 압박이 생길 수 있다. 실제 GPU 사용량·OOM을 측정한 결과는 아니며, 작업 종료가 보장되지 않는 제어 흐름을 확인했다. 모든 종료가 무한 연산을 만든다는 뜻은 아니다. 모델이 자체 종료하면 작업도 끝나지만, 그때까지 소비자와 작업의 수명이 어긋난다.

**수정 방향:** 소비자의 finally에서 취소 신호를 전달하고 생성 루프가 이를 확인하도록 중단 조건을 연결한다. 협력적 중단과 제한된 대기를 적용하며, 작업이 아직 살아 있는 동안 종료가 끝난 것처럼 재시도를 허용하지 않는 정책도 필요하다. 단순히 join을 무기한 기다려 원래의 대기를 되살리지 않는다.

**완료 확인 조건:** 정상 완료, 첫 토큰 전 오류, 일부 토큰 후 오류, 소비자 타임아웃, 소비자 close에서 작업 종료·오류 전달을 구분해 확인한다.

**베이스라인 영향:** 현재 설정에서 활성화된 API 중심 베이스라인이라면 이 항목을 로컬 사용 전 후속 작업으로 명시할 수 있다. 로컬 경로까지 완료했다고 확정하려면 먼저 보완한다. Stage 3의 미정 결정 자체를 문제로 삼은 것은 아니다.
