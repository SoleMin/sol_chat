## 2. 잘 구성된 부분과 효율성 평가

- 코어·서버·화면·학습 코드의 책임 분리가 분명하다. `ChatBackend` 인터페이스와 생성기 주입으로 실제 API 없이 주요 흐름을 테스트할 수 있다.
- API와 로컬 백엔드를 필요할 때 가져오므로 일반 API 사용자에게 무거운 학습 패키지 설치를 강제하지 않는다.
- 모델 입력의 과거 턴 수·글자 수 제한, 세션 수 제한, 사용자 입력 검증이 이미 있다. API 오류를 사용자 메시지로 바꾸고 실패한 답변을 정상 대화로 저장하지 않는 방향도 적절하다.
- 웹 메시지를 `textContent`로 표시하는 점과 테스트에서 클라이언트별 대화를 분리하는 점이 좋다.
- 기본 최대 10턴에서 전처리의 반복 합산·슬라이싱을 우선 최적화할 근거는 부족하다. 실제 우선순위는 아래의 중복 초기화와 보관 데이터 증가다.

정량 지연시간·처리량·실제 GPU 메모리 벤치마크는 수행하지 않았다. 따라서 전반적인 속도가 빠르다고 판정한 것은 아니다.

## 3. 확인된 문제

P2는 특정 사용 조건에서 실제 오류나 자원 낭비를 일으키므로 후속 수정이 필요한 문제를 뜻한다. 아래 수정 방향은 제안이며, 이번 평가에서 소스 수정은 하지 않았다.

| --- | --- | --- | --- | --- |
| B-001 | P2 | 백엔드 첫 초기화가 중복 실행됨 | 같은 모델에 첫 요청이 겹침 | `chatbot/generation.py:32–34` |
| B-002 | P2 | 로컬 생성 실패 시 스트림이 계속 대기함 | 로컬 모델의 생성 스레드에서 예외 발생 | `chatbot/backends/local_backend.py:86–89` |

### B-001. 백엔드 캐시의 초기화가 원자적이지 않음

**근거:** 캐시에 없다는 확인과 `backend_factory(entry)` 호출 사이에 동기화가 없다. 동기식 FastAPI 핸들러에서 같은 `ChatGenerator`를 공유하므로 첫 요청 두 개가 겹치면 두 요청 모두 초기화를 시작할 수 있다.

**재현:** 팩토리에 두 스레드를 만나는 barrier를 넣어 원본 `backend()`를 동시 호출했다. 생성된 백엔드는 2개, 최종 캐시 항목은 1개였다.

**영향:** API 클라이언트 중복 생성과 초기화 낭비가 발생한다. 로컬 백엔드에서는 모델을 두 번 로드해 메모리 부족으로 이어질 수 있다. 실제 GPU OOM을 실행해 확인한 것은 아니며, 모델이 중복 생성되는 경쟁 조건을 확인했다.

**수정 방향:** 모델별 초기화 잠금 또는 초기화 결과를 공유하는 장치를 둔다. 비용이 큰 생성 작업은 한 번만 실행하고 실패 시 재시도가 가능하게 한다.

**회귀 확인:** 같은 모델에 최초 요청을 동시에 여러 개 보내도 팩토리는 한 번만 호출되고, 서로 다른 모델은 불필요하게 직렬화되지 않는지 확인한다.

### B-002. 생성 스레드의 예외가 스트림 소비자에게 전달되지 않음

**근거:** `Thread(target=self.model.generate, ...)`에 예외 전달·종료 보장 처리가 없다. 소비자는 타임아웃을 지정하지 않은 `TextIteratorStreamer`에서 계속 읽는다. 생성 스레드가 종료 신호를 보내기 전에 실패하면 소비자는 결과를 기다린다.

**재현:** 원본 `stream()` 메서드를 AST로 추출하고, 큐에서 대기하는 스트리머 대역 및 `RuntimeError('CUDA out of memory')`를 발생시키는 모델 대역으로 실행했다. 생성 오류가 기록됐지만 소비자 오류는 없었고, 생성 스레드 실패 이후에도 소비자는 대기 중이었다.

**영향:** 로컬 모델을 선택한 웹에서 답변이 끝나지 않고 입력 잠금이 풀리지 않을 수 있다. 요청 작업도 반환되지 않는다. 이는 실제 GPU 실행 결과가 아니라 원본 제어 흐름에 대한 격리 재현이다.

**수정 방향:** 작업 스레드의 오류를 소비자에게 전달해 `BackendError`로 변환하고, 성공·실패 모두 스트리머의 종료를 보장한다. 제한 시간을 보조적으로 두되 타임아웃만 추가하고 생성 스레드 정리를 놓치지 않도록 한다.

**회귀 확인:** 첫 토큰 전 오류와 일부 토큰 후 오류 모두 SSE `error`로 종료되는지 확인한다.

### B-003. 모델 입력 제한이 실제 보관량을 제한하지 않음

**근거:** `add_exchange()`는 세션의 `messages`에 계속 추가한다. `trim_history()`는 모델 호출용 목록만 자르고, 저장된 원본은 줄이지 않는다. 활성 세션은 응답마다 `updated_at`이 갱신돼 TTL 만료도 계속 미뤄진다. 이는 메모리 저장 자체에 대한 지적이 아니라, PLAN D-008에 명시한 세션당 상한이 실제 보관에 적용되지 않는 문제다.

**재현:** 같은 세션에 1,000턴을 추가하자 2,000개 메시지, 내용 3,000,000자가 보관됐다. 기본 설정에서 모델 입력에 남는 과거 대화는 4턴뿐이었다. 이 수치는 문자 수이며 프로세스의 실제 메모리 사용량 측정치는 아니다.

**영향:** 오래 사용하는 세션은 메모리가 계속 증가하고, 전처리는 매번 전체 기록을 순회한다. 세션 상세 API도 전체 기록을 보내므로 전송량과 화면 복원 비용이 커진다. 세션 개수 500개 제한만으로는 전체 보관량이 제한되지 않는다.

**수정 방향:** 세션 보관 자체에 턴·글자 또는 바이트 상한을 적용한다. 화면의 전체 기록을 유지하고 싶다면 모델 컨텍스트와 화면 기록의 보관 정책을 분리하되 각각의 자원 상한을 명시한다.

**회귀 확인:** 설정 상한보다 충분히 많은 턴을 저장해도 보관량이 상한 안에서 유지되고, 잘린 대화가 user/assistant 쌍을 유지하는지 확인한다.

### B-004. 스트림 종료와 답변 완료를 구분하지 않음

**근거:** `reader.read()`의 `done`이 참이면 즉시 루프를 나간다. 서버가 정의한 정상 완료 이벤트인 SSE `done`을 받았는지 확인하지 않는다. `sendMessage()`는 예외나 `error` 이벤트가 없으면 성공 경로로 처리한다.

**재현:** 원본 `streamChat()`에 `session`, `token` 두 이벤트만 전달하고 EOF로 종료하는 모의 응답을 넣었다. `done`/`error`가 없는데도 Promise가 정상 이행됐다. 브라우저 실사용이 아니라 Node VM에서 원본 함수를 실행한 결과다.

**영향:** 종료 이벤트 없이 연결이 닫히는 경우 불완전한 답변이 정상 답변처럼 보인다. 서버가 저장 전에 끊겼다면 화면에 보이는 내용과 재접속 후 기록이 달라질 수도 있다. 모든 네트워크 단절이 이 경로를 탄다는 뜻은 아니며, `reader.read()`가 예외를 던지는 단절은 기존 catch로 처리된다.

**수정 방향:** 종료 이벤트 수신 여부를 기록하고, 종료 이벤트 없는 EOF는 미완료 오류로 처리한다. 서버에 저장됐는지가 불명확한 경우 세션을 다시 조회해 표시를 맞춘다.

**회귀 확인:** 정상 완료, 명시적 오류, 종료 이벤트 없는 EOF, 읽기 예외를 각각 구분해 검증한다.

### B-005. 인증 실패 제한이 추가 비밀번호 검증을 막지 않음

**근거:** 비밀번호 비교가 `auth_fail.hit()`보다 먼저 실행되고, 일치하면 즉시 성공한다. 실패 제한을 초과한 뒤에도 후보 비밀번호를 계속 대조하므로, 공격자는 실패 응답이 429로 바뀐 상태에서도 맞는 후보를 200으로 구별할 수 있다.

**재현:** 실패 제한을 2회로 설정하고 같은 IP에서 `wrong1`, `wrong2`, `wrong3`, 실제 테스트 비밀번호 순으로 요청했다. 결과는 `[401, 401, 429, 200]`이었다.

**영향:** 설정한 실패 제한이 실질적인 추측 횟수 제한으로 작동하지 않는다. 다만 상위 전체 API 제한은 여전히 유효하다. 기본값 기준 무제한 인증 시도가 가능하다는 뜻은 아니며, 인증 실패 10회라는 별도 보호가 전체 API 120회 범위까지 검증을 계속 허용하는 문제다.

**수정 방향:** 해당 IP가 실패 한도를 넘었는지 비밀번호 비교 전에 검사한다. 정상 인증까지 잠시 제한하는 정책을 원하지 않는다면 별도 인증 시도 제한을 두어 추측값 검증 자체의 빈도를 제한한다.

**회귀 확인:** 실패 제한 초과 후에는 정답 후보도 정책상 제한되는지, 시간이 지나면 다시 인증 가능한지 확인한다. 전체 API 제한과 별개로 검사한다.

### B-006. 세션 잠금이 대화 한 턴 전체를 보호하지 않음

**근거:** 저장소 잠금은 메시지 추가 구간에만 적용된다. 요청마다 과거 기록을 읽고 답변을 생성한 다음 저장하므로, 같은 세션의 두 생성 작업이 동시에 같은 과거 기록을 볼 수 있다. 프론트의 `busy`는 해당 탭에만 유효하다.

**재현:** 같은 세션에 서로 다른 질문을 동시에 보내고 대역 백엔드에서 두 생성 작업이 모두 시작될 때까지 대기시켰다. 두 요청 모두 200이었고, 각 모델 입력에는 자기 질문 하나만 있었다. 이후 저장된 대화는 두 턴이 연속된 대화처럼 나열됐다.

**영향:** 표시된 기록에서는 뒤의 답변이 앞의 턴을 알고 생성된 것처럼 보이지만 실제로는 앞의 질문·답변을 보지 못했다. 답변 완료 순서에 따라 저장 순서도 달라질 수 있다. 사전 학습 기능이나 다중 사용자 계정 도입과 무관하게 두 탭만으로 발생 가능한 기존 멀티턴 정합성 문제다.

**수정 방향:** 세션 단위로 생성 시작부터 저장까지 직렬화하거나, 생성 중 같은 세션의 추가 요청을 명시적으로 거절한다. 전역 잠금으로 모든 세션의 모델 호출을 묶지는 않는다.

**회귀 확인:** 같은 세션의 두 요청은 정책에 따라 순차 처리되거나 충돌 응답을 받고, 서로 다른 세션의 요청은 계속 병렬 처리되는지 확인한다.

## 4. 우선순위가 낮은 효율성 관찰

`server/security.py:26–38`의 요청 제한 저장소는 같은 키가 다시 요청할 때만 오래된 타임스탬프를 지우고, 더 이상 접속하지 않는 IP의 키 자체는 정리하지 않는다. 모의 시간으로 1,000개 IP를 등록하고 120초가 지난 뒤 새 IP로 요청해도 키는 1,001개 남았다. 장기 실행 및 접속 IP가 많은 환경에서는 주기적 키 정리를 고려할 수 있다. 현재 토이 프로젝트 규모의 실제 메모리 영향은 측정하지 않아 위 6건과 분리했다.
